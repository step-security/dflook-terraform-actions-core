# dflook-terraform-actions-core

Shared implementation behind the StepSecurity maintained replacements for the
[dflook Terraform actions](https://github.com/dflook/terraform-github-actions).

This is not an action. It is the library those actions are built from:

| Action | Uses this for |
| --- | --- |
| [dflook-terraform-fmt-check](https://github.com/step-security/dflook-terraform-fmt-check) | version selection, tool download |
| [dflook-terraform-check](https://github.com/step-security/dflook-terraform-check) | the above, plus backend init |
| [dflook-terraform-apply](https://github.com/step-security/dflook-terraform-apply) | the above, plus plan handling and PR comments |

## Why it exists

Each of those actions is a thin entrypoint — 24 to 191 lines — over a large
shared setup step: deciding which Terraform or OpenTofu version to run,
downloading and verifying it, assembling backend configuration and credentials.
Upstream solves this by shipping one container image with many entrypoints. We
publish a library instead, bundled into each action at build time, so the
behaviour lives in one place.

## Consuming it

Actions depend on this repository directly; there is no registry involved.

```json
{
  "dependencies": {
    "@step-security/dflook-terraform-actions-core": "github:step-security/dflook-terraform-actions-core#v0.1.0"
  }
}
```

The dependency is build-time only. Each action bundles it into its own committed
`dist/index.js`, so nothing is installed by anyone using the actions.

## Verification

Behaviour has to match upstream exactly, so the tests compare against upstream
rather than against our own expectations:

- **Version constraints** are checked against a matrix generated by running
  upstream's own `terraform/versions.py` — 432 combinations of operator, bound
  and version.
- **Module reading** is checked against `python-hcl2` 7.3.1, the parser and
  version upstream pins, over the Terraform fixtures in its test suite.

Regenerating either after an upstream change is how we detect drift.
